# 0001. Vite + React で静的 SPA として作る

- 状態: 採用
- 日付: 2026-08-12

## 背景

旧アプリは Next.js 16 (App Router) + React 19 で作られていました。しかし実態は
**完全なクライアントサイドアプリ**で、サーバー側の機能を一切使っていません。

- ページは 1 つ (`app/page.tsx`) のみ。ルーティング不要
- Server Component も Server Action も API Route も未使用
- 全コンポーネントが `"use client"`
- データはブラウザ内 (IndexedDB) にのみ保存。サーバーとの通信なし

この構成では、Next.js が提供する機能のほとんどが使われないまま、
その複雑さ (App Router の規約、サーバー / クライアント境界、ビルドの重さ) だけを
負担している状態でした。

## 選択肢

### 案 A: Next.js を維持する

- 移行コストがゼロ
- 既存の知見とテストが流用できる
- ただし、上記の負担は残る。SSR しないのに `"use client"` を全ファイルに書き、
  クライアント専用の処理を `useEffect` に押し込む必要がある

### 案 B: Vite + React に移す

- ビルドと開発サーバーの起動が速く、テストも Vitest で統一できる
- 静的ファイルのみを出力するので GitHub Pages にそのまま置ける
- クライアント専用であることが構成に素直に表れる
- 移行コストがかかる (ただし今回はどうせ全面的に作り直す)

### 案 C: React 以外 (Svelte / Vue) に移す

- 状態管理の書き味が良くなる可能性はある
- しかし React の知見・エコシステム (Testing Library, Playwright との組み合わせ) を
  捨てる理由が弱い。今回の作り直しの目的は UI の再設計であって、
  フレームワークの乗り換えではない

## 決定

**案 B (Vite + React 19 + TypeScript)** を採用します。

サーバー機能を使わないアプリに Next.js を使う理由がなく、今回は全面的に作り直すため
移行コストを払う機会でもあります。React を維持するのは、UI の再設計に集中するためです。

配信は GitHub Pages。ビルド成果物は `dist/` の静的ファイルのみです。

## 結果

得られるもの:

- 開発サーバーの起動とテストの実行が速くなる
- `"use client"` とサーバー / クライアント境界を意識しなくてよい
- ビルド成果物が静的ファイルだけなので、配信先を選ばない

諦めるもの:

- SSR / SSG による初期表示の最適化 (エディタなので初期表示より操作性が重要)
- 将来サーバー機能 (クラウド保存・共有リンクの短縮) が必要になった場合、
  別途バックエンドを用意するか、この決定を見直す必要がある

見直す条件: サーバー側の処理 (アカウント、共有、生成物のビルド) が必要になったとき。

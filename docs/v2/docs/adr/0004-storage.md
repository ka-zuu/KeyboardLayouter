# 0004. IndexedDB を主ストレージにする

- 状態: 採用
- 日付: 2026-08-12

## 背景

サーバーを持たないため、ユーザーの作業内容はブラウザ内に保存します。
選択肢と制約は以下のとおりです。

- レイアウト 1 つは数十 KB 程度。複数プロジェクトを持つと数 MB になり得る
- 自動保存が必要 (エディタで作業を失わせない)
- 保存処理がドラッグ操作を止めてはいけない

旧アプリは IndexedDB を主とし、`localStorage` をフォールバックにする構成でした。
この判断自体は妥当なので踏襲します。

## 選択肢

### 案 A: `localStorage` のみ

- 実装が最も簡単 (同期 API)
- **容量が概ね 5MB で、超えると例外が出る**。プロジェクトが増えると詰む
- 同期 API なので、大きなデータの書き込みがメインスレッドを止める

### 案 B: IndexedDB を主、`localStorage` をフォールバック

- 容量が実質的に問題にならない
- 非同期なのでメインスレッドを止めない
- API が煩雑 (`onupgradeneeded` / トランザクション)。ただし薄いラッパを書けば済む
- プライベートブラウジングや設定で IndexedDB が使えない環境がある → フォールバックが必要

### 案 C: OPFS (Origin Private File System) / File System Access API

- ファイルとして扱えるため、大きなデータに強い
- **Safari と Firefox で `showSaveFilePicker` などの対応が揃っていない**
- 「ユーザーが選んだファイルに保存する」用途としては魅力があるが、
  自動保存の基盤としては対応状況が不足

## 決定

**案 B** を採用します。旧アプリ (`lib/idb.ts`, `lib/storage.ts`) の構成を踏襲します。

| 項目 | 決定 |
|---|---|
| データベース名 | 新しい名前を使う (旧アプリの `mkd-db` とは分ける) |
| ストア名 | `keyval` (キー・値ストア 1 つ) |
| 書き込み | 1000ms のデバウンス。連続更新中は最後の状態だけを書く |
| フォールバック | IndexedDB が使えない、または書き込みが失敗したら `localStorage` へ |
| 旧データ | 旧アプリのキーを読んで移行する。**旧データは削除しない** ([../MIGRATION_FROM_MKD.md](../MIGRATION_FROM_MKD.md#ブラウザに残ったデータの取り込み)) |

保存するキーは 3 つに分けます (旧アプリは 1 つのキーに全部入れていました)。

| キー | 内容 | 理由 |
|---|---|---|
| `projects` | `Record<string, ProjectModel>` | 本体 |
| `currentProjectId` | `string` | 小さく頻繁に変わるため分ける |
| `editorPrefs` | `{ gridSize, snapEnabled, theme }` | プロジェクトと独立に保持したい |

**File System Access API は補助的に使います。** 「名前を付けて保存」「開く」で
対応ブラウザではネイティブのファイルダイアログを使い、非対応ブラウザでは
`<a download>` と `<input type="file">` にフォールバックします。
これは自動保存とは別の機能で、ユーザーが明示的にファイルを扱う場合の利便性のためです。

## 結果

得られるもの:

- 容量の心配がなくなる
- ドラッグ中に保存が走ってもメインスレッドが止まらない
- 旧アプリのユーザーがデータを引き継げる

諦めるもの / リスク:

- 非同期処理のため、「保存済み」の状態表示が必要になる
  (ステータスバーに保存状態を出します)
- ブラウザのデータ削除でユーザーのデータが消える。対策として、
  起動時に「ブラウザ内にのみ保存されている」ことを一度案内し、
  JSON エクスポートによるバックアップを促します
- タブを複数開いた場合の競合。最後に書いた方が勝つ (Last Write Wins) とし、
  `BroadcastChannel` で他タブに変更を通知して警告を出すのは M6 以降の課題とします

見直す条件: 複数タブでの編集を正式にサポートする必要が出たとき。

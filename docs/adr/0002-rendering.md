# 0002. キャンバスは SVG で描く

- 状態: 採用
- 日付: 2026-08-12

## 背景

キーボードレイアウトの描画方式を決める必要があります。要件は:

- 数十〜1000 個程度のキーを表示し、パン・ズームできる
- 矩形以外の形状 (ISO Enter, ステップド, Big-Ass Enter) を正確に描く
- キーごとの回転 (回転中心が幾何中心でない場合も含む)
- クリック・ドラッグでの選択と移動
- 刻印を最大 12 スロット表示
- E2E テストから検証できる

旧アプリは Konva (`react-konva`) を使っていました。動作はしていましたが、

- Canvas 上に描かれるため、E2E テストからキーを個別に検証できない
  (旧アプリはテスト用にストアを `window` に露出させる回避策を入れていた)
- ヒットテスト・回転ハンドル・選択枠をすべて自前で実装する必要がある
- Konva 本体が依存として重い

という難点がありました。

## 選択肢

### 案 A: Konva を継続

- 実装の移植が楽
- 大量オブジェクトの描画性能は実績がある
- 上記の難点は残る

### 案 B: SVG (React でそのまま要素を出す)

- 形状を `<path>` で正確に書ける。ISO Enter の輪郭がそのまま書ける
- 回転は `transform="rotate(angle cx cy)"` で表現でき、回転中心を素直に扱える
- 刻印はテキスト要素になり、ブラウザのフォント描画とアクセシビリティに乗る
- クリック判定をブラウザに任せられる部分が多い
- E2E テストから `data-testid` で個々のキーを検証できる
- 要素数が増えると DOM が重くなる (1 キーあたり数要素 × 1000 キー)

### 案 C: 自前の Canvas 2D レンダラ

- 描画性能を最も細かく制御できる
- ヒットテスト・テキスト配置・選択表示をすべて自前で書く必要があり、
  初期コストが最も高い

## 決定

**案 B (SVG) を既定とし、描画層をインタフェースで差し替えられるようにする**ことを
採用します。

判断の理由は、このアプリで支配的なのは「正確な形状」「編集のしやすさ」「テスト可能性」で
あり、描画性能は 1000 キー程度なら SVG でも実用範囲に収まると見込めるためです。
性能が問題になった場合に備えて、描画層は次のインタフェース越しに使います。

```ts
export interface LayoutRenderer {
  mount(container: HTMLElement): void;
  render(scene: RenderScene): void;
  hitTest(pointPx: { x: number; y: number }): string | null;
  dispose(): void;
}
```

`RenderScene` はストアの型ではなく、描画に必要な情報だけを持つ平坦な構造にします。
Canvas 実装を後から追加するときに、UI パネル側を触らずに済みます。

## 結果

得られるもの:

- 形状と回転の表現が素直になり、副矩形を持つキーを正しく描ける
- E2E テストがキー単位で書ける。ストアを `window` に露出させる回避策が不要になる
- 依存が 1 つ減る

諦めるもの / リスク:

- 1000 キー超での DOM 要素数。対策として:
  - 表示範囲外のキーを描かない (ビューポートカリング)
  - ズームアウト時は刻印を省略する (`scale` が小さいときはテキストを出さない)
  - 1 キーあたりの要素数を抑える (影は CSS、グリッドは 1 枚の `<pattern>`)
- 性能目標 ([../TESTING.md](../TESTING.md#性能テスト)) を満たせない場合は、
  この ADR を破棄せず Canvas 実装を追加して切り替えます
  (インタフェースを用意しているのはそのためです)。

見直す条件: 上記の対策を入れても性能目標を満たせないことが計測で示されたとき。

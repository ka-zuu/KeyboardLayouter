# 0003. Zustand + 自前のスナップショット履歴

- 状態: 採用
- 日付: 2026-08-12

## 背景

エディタなので Undo / Redo が必須です。旧アプリは Zustand + Zundo (`temporal`) を
使い、`partialize` で `project` のみを履歴対象にしていました。

これで概ね動いていましたが、次の点が扱いにくくなっていました。

- ドラッグ中の連続更新がそのまま履歴に積まれないよう調整する必要がある
  (旧アプリは `limit: 50` と `equality: shallow` で緩和していたが、
  「ドラッグ 1 回 = 履歴 1 段」を明示的に表現できていない)
- 履歴に積まれる単位が「状態の差分」であり、**何の操作だったか**を持たない。
  そのため Undo ボタンに「キーの移動を取り消す」のような説明を出せない
- ライブラリの都合 (`useStore.temporal.getState()` のような呼び出し) が
  UI コードに漏れる

## 選択肢

### 案 A: Zundo を継続

- 実装コストが最小
- 上記の扱いにくさは残る

### 案 B: コマンドパターン (操作と逆操作を持つ)

- 履歴 1 段が「操作」そのものになり、説明を出せる
- メモリ効率が良い
- すべての操作に逆操作を正しく実装する必要があり、実装量と間違いのリスクが大きい
  (特に「マトリクス自動割り当て」のような多数のキーを一括で変える操作)

### 案 C: 自前のスナップショット履歴 + 操作ラベル

- 「操作後のプロジェクト全体」と「操作の名前」を組で積む
- 逆操作を書く必要がない (スナップショットを差し替えるだけ)
- キー 1000 個 × 50 段のメモリを消費する

## 決定

**案 C** を採用します。

`ProjectModel` はプレーンなオブジェクトで、編集操作は
`(project, args) => project` の純関数として書きます
([../ARCHITECTURE.md](../ARCHITECTURE.md#状態管理と履歴))。
このため、スナップショットを積むのが最も単純で間違いが少ない方法になります。

```ts
export interface HistoryEntry {
  project: ProjectModel;
  /** UI に出す操作名 (例: 'キーの移動')。 */
  label: string;
  /** 同じ id の連続した操作は 1 段にまとめる (ドラッグ中の更新など)。 */
  coalesceKey: string | null;
}

export interface History {
  push(entry: HistoryEntry): void;
  undo(): HistoryEntry | null;
  redo(): HistoryEntry | null;
  readonly canUndo: boolean;
  readonly canRedo: boolean;
  /** 直近の操作名 (ツールチップ用)。 */
  readonly undoLabel: string | null;
  readonly redoLabel: string | null;
}
```

- 上限は 50 段 (旧アプリと同じ)。
- `coalesceKey` により「ドラッグ中の連続移動」を 1 段にまとめます。
  ドラッグ開始時に一意な値を割り当て、終了時に `null` に戻します。
- 履歴に積むのは `ProjectModel` のみ。選択・ズーム・パンは積みません
  (旧アプリと同じ方針。ただし選択はモデル外に出したので、混入の余地自体がなくなります)。

メモリ量の見積り: キー 1 個あたり約 300 バイト (JSON 換算) として、
1000 キー × 50 段で約 15MB。構造共有 (変更のないキーのオブジェクトは
そのまま使い回す) が効くため実際にはこれより小さくなります。
編集操作を純関数で書き、変更のないキーを新しいオブジェクトにしないことが
この前提です。

## 結果

得られるもの:

- Undo / Redo に操作名を出せる
- ドラッグ 1 回が履歴 1 段になることをコードで明示できる
- 履歴の実装が数十行で読み切れる。ライブラリの都合が UI に漏れない
- 依存が 1 つ減る

諦めるもの / リスク:

- メモリ使用量。1000 キーを超える巨大なレイアウトで問題になった場合は、
  段数を減らす (50 → 20) か、コマンドパターン (案 B) への移行を検討します
- 「構造共有が効いていること」を保つ規律が必要。編集コマンドが
  全キーを作り直す実装になっていないか、レビューで確認します
  (`tests/perf/` で 50 段積んだ後のメモリを計測します)

見直す条件: 実測でメモリが問題になったとき。
